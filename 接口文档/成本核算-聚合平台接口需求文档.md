# 成本核算 · 聚合平台接口需求文档

> 本文档由 **new-api（下游 / 调用方）** 提出，描述 **聚合平台（上游 / 被调用方）** 需要对外提供的接口。

> 展示背后每一家真实供应商的倍率 / 成本 / 可用性 / 缓存 / tokens，并与渠道级兜底口径做对照。

## 1. 背景与目标

### 1.1 我方的成本模型

new-api 侧对每个渠道已有一套**兜底成本口径**：

```
刊例$   list_usd    = 由日志重算的模型刊例价消耗（未打折的原价）
成本¥   cost_cny    = list_usd × 渠道成本倍率(CNY:USD)      # cost_mode = "ratio"
        或          = list_usd × 成本折扣 × 查询汇率         # cost_mode = "discount"
收入¥   revenue_cny = 用户实付额度 / QuotaPerUnit × 查询汇率
利润¥   profit_cny  = revenue_cny − cost_cny
```

对于**聚合渠道**（渠道设置中 `is_aggregator = true`，背后是贵方聚合平台），上述倍率只是一个**加权平均的估算值**：
聚合平台背后可能同时挂着 A/B/C 三家供应商，每家的真实结算倍率、可用性、缓存命中情况都不同。
new-api 的日志无法把单次请求归属到具体某一家子供应商，**只有聚合平台自己知道**。

### 1.2 我们需要贵方提供什么

> 一句话：**给定一个时间区间，返回这段时间内每一家上游供应商各自的消耗、成本、倍率、可用性与 token 明细。**

拿到后 new-api 会：

1. 落库到快照表 `channel_upstream_snapshots`；
2. 在成本核算页面「供应商维度」的聚合渠道行下展开子表；
3. 做「渠道兜底口径 vs 上游真实成本」对照，暴露倍率填错、上游涨价、某家供应商可用性塌方等问题。

### 1.3 明确不需要的

- ❌ 不需要单条请求级明细（数据量大且我方日志已有）；
- ❌ 不需要贵方的用户 / 令牌 / API Key 等身份数据；
- ❌ 不需要贵方的售价 / 利润数据——我方只关心**我方付给贵方背后各家供应商的成本**；
- ❌ 不需要写接口，本文档描述的全部是**只读查询**。

## 2. 通信与鉴权

### 2.1 基础地址

聚合平台提供一个 Base URL，例如 `https://aggregator.example.com`。
new-api 侧默认复用**渠道配置里已有的 Base URL 与 Key**（与现有上游倍率同步 `FetchUpstreamRatios` 的做法一致，见 `controller/ratio_sync.go:277`）：

```
请求地址 = <渠道 Base URL> + <本文档定义的路径>
```

如需独立的成本查询地址 / 令牌，我方可在渠道设置中单独配置（`ChannelSettings` 增加 `upstream_api` 配置块），贵方无需关心。

### 2.2 鉴权

```http
Authorization: Bearer <token>
```

要求：

| 项 | 要求 |
|---|---|
| 令牌类型 | Bearer Token，长期有效或支持我方配置更换 |
| 权限范围 | **只读、仅成本统计**。禁止该令牌具备调用模型、修改配置、查看用户数据的能力 |
| 传输 | 强制 HTTPS，禁止把令牌放在 query string |
| 失效行为 | 令牌无效时返回 `401`（见 §8），我方会停止重试并在渠道上标红提示 |

### 2.3 请求头

| Header | 必填 | 说明 |
|---|---|---|
| `Authorization` | ✅ | `Bearer <token>` |
| `Accept` | — | `application/json` |
| `X-Client` | — | 我方会带 `new-api-cost/1` 便于贵方侧排查 |

### 2.4 超时、重试与并发

| 项 | 我方行为 | 对贵方的要求 |
|---|---|---|
| 超时 | 默认 30s（可配 10–120s） | 单次查询请在 30s 内返回；超过请改用 §5 分页 |
| 重试 | 5xx / 网络错误按指数退避重试最多 3 次（1s / 2s / 4s） | 接口需**幂等**：同参数重复查询结果必须一致 |
| 并发 | 每个渠道串行，多渠道最多 4 并发 | 无需支持高并发 |
| 频率 | 手动点击「从上游同步」触发；后续可能加定时任务，最快 5 分钟一次 | 限流阈值请不低于 12 次/小时/令牌 |

## 3. 统一响应封装

所有接口统一返回 HTTP `200` + 下述信封（与 new-api 自身 API 约定一致）；仅鉴权 / 限流 / 服务端错误使用非 200 状态码（见 §8）。

```jsonc
{
  "success": true,        // 业务是否成功
  "message": "",          // 失败时的可读原因（会原样展示给我方管理员，请写人话）
  "data": { }             // 业务数据，失败时可为 null
}
```

## 6. 字段口径定义（核心章节）

> 本章是本文档最重要的部分。字段名对上但口径对不上，报表会给出**看起来合理但完全错误**的数字，比接口没实现更危险。

### 6.1 时间区间：Unix 秒，左闭右开

```
[start_timestamp, end_timestamp)     即  start <= t < end
```

- **单位是秒**，不是毫秒。
- **左闭右开**是硬性要求。若贵方实现成闭区间 `[start, end]`，我方连续按天拉取时会在每个边界秒**重复计一次**，日累计误差随请求量放大。
- 归属时间以**请求完成/计费时刻**为准，并在贵方内部保持一致；不要一部分按开始时间、一部分按结束时间归属。
- 我方查询区间上限 370 天。若贵方有更严格的上限（如 90 天），请在 §8 用 `400` + 明确 message 告知，我方会分段拉取。

### 6.2 ⚠️ Token 口径：四项必须互不重叠

这是我方系统内部刚刚修复过的一类真实缺陷，请特别注意。

上游厂商对 `prompt_tokens` 有两种互不兼容的语义：

| 语义 | 代表厂商 | 含义 |
|---|---|---|
| `exclusive`（互斥） | Anthropic / Claude | `input_tokens` 与 `cache_read` / `cache_creation` **互斥**，三者相加才是总输入 |
| `inclusive`（含缓存） | OpenAI / Gemini / DeepSeek / 智谱 / Moonshot | `prompt_tokens` **已包含** `cached_tokens` |

**我方要求：**

1. **首选**：`prompt_tokens` 直接返回**非缓存输入**（即已扣掉 `cache_read_tokens`），并声明 `usage_semantic: "exclusive"`。
2. **次选**：保持上游原样，但**必须**如实声明 `usage_semantic: "inclusive"`，我方会自行做 `prompt_tokens − cache_read_tokens` 归一化。
3. 若贵方背后混合了两种语义的上游，**请在每个 `suppliers[]` 行上单独声明** `usage_semantic`，顶层声明作为默认值。
4. ❌ **最差情况：不声明且口径混合。** 这会让缓存命中率出现 >100% 或系统性偏低，且无法从数据侧发现。若确实无法保证，请在 `message` 中明确告知，我方会禁用该渠道的 token 相关列而不是展示错误数字。

归一化后，以下恒等式**必须成立**：

```
总输入 tokens = prompt_tokens(非缓存输入) + cache_read_tokens + cache_creation_tokens
总 tokens     = 总输入 + completion_tokens
缓存命中率     = cache_read_tokens / 总输入          # 分母不含输出，输出永不可能命中缓存
```

**`cache_creation_tokens` 特别说明**：Anthropic 的 5 分钟 / 1 小时两档缓存写入（`cache_creation_input_tokens_5m` / `_1h`）是**总量的拆分项**，不是独立增量。请返回**总量**，不要把总量与拆分项相加（我方系统曾因此把缓存创建量算成两倍）。

### 6.3 金额口径

| 字段 | 定义 |
|---|---|
| `usage_usd` | **刊例消耗美元**：按模型官方标价（未打折）折算的美元消耗。这是我方与贵方共同的计费基数 |
| `cost_cny` | **真实成本人民币**：我方实际需要为这部分消耗支付给该供应商的金额 |
| `cost_ratio` | CNY:USD 倍率。语义为「每消耗刊例 $1，实付 ¥cost_ratio」。例：`2.5` 表示刊例 $1 记成本 ¥2.50 |
| `cost_discount` | 折扣系数，仅 `cost_mode = "discount"` 时有意义。例：`0.8` = 刊例价 8 折 |

- `usage_usd` 必须是**净额**：已扣除退款、失败请求的预扣返还等（见 §7.3）。
- `cost_cny` 是**权威值**。当 `cost_cny` 与 `usage_usd × cost_ratio` 不一致时，我方以 `cost_cny` 为准，并在超出容差时提示（见 §7.1）。
- 数值类型为 JSON number，最多 6 位小数；**禁止**科学计数法（`1.2e3`）、千分位（`1,234.5`）、货币符号（`$1234`）和字符串包装（`"1234.5"`）。
- 无消耗时返回 `0`，不要返回 `null` 或省略字段。

### 6.4 币种

`currency` 固定 `"CNY"`，`cost_cny` 为人民币。
若贵方与某家供应商以美元结算，请**在贵方侧按结算时汇率折算成 CNY 后返回**，并把原始币种与汇率放进 `extra`：

```jsonc
"extra": { "settle_currency": "USD", "settle_amount": 420.1, "fx_rate": 7.15 }
```

我方不做币种换算——汇率口径必须由掌握结算事实的一方确定。

### 6.5 `supplier_name` 稳定性

- 必须是**跨查询稳定**的标识。同一家供应商在不同时间区间的查询中必须返回同一个 `supplier_name`，否则快照会分裂成多行、趋势断档。
- 建议与我方渠道设置中 `sub_suppliers[].name` 保持一致（我方管理员手工填写的名称）。若不一致，我方按 `supplier_name` 为准新增行，管理员需手工对齐。
- 若供应商需要改名，请保持 `supplier_id` 不变，我方以 `supplier_id` 续接历史。
- ❌ 不要在名字里带时间、批次号或随机后缀。

### 6.6 请求数、失败数与可用率

| 字段 | 定义 |
|---|---|
| `request_count` | 区间内**成功**的请求数 |
| `error_count` | 区间内**失败**的请求数 |
| `availability` | `request_count / (request_count + error_count)`，取值 0–1 |

- **「失败」的判定**：仅统计**上游侧**导致的失败（5xx、超时、连接失败、上游限流 429、上游内容策略拒绝）。
  ❌ **不要**把客户端参数错误（400 参数非法、401 令牌无效、404 模型不存在）计入 `error_count`——否则可用率会被下游用户的错误用法污染，失去运维指标的意义。
- 流式请求以**是否成功建立并完整结束流**为准；中途断流计失败。
- **请优先返回 `request_count` 与 `error_count` 这两个可加和的原始值**，`availability` 可省略。原因见 §6.7。

### 6.7 ⚠️ 派生字段纪律：只返回可加和的原始值

**规则：凡是「比率 / 平均值」类指标，请返回其分子与分母，而不是算好的结果。**

因为我方会把多个区间、多家供应商的快照再次汇总。**比率不能相加，也不能简单求平均**——对不同规模的行取算术平均会得到错误结论（1 次请求 100% 可用 + 10000 次请求 50% 可用，平均不是 75%）。

| 想要的指标 | ❌ 只给这个 | ✅ 请给这个 |
|---|---|---|
| 可用率 | `availability: 0.99` | `request_count` + `error_count` |
| 平均首字延迟 | `avg_ttft_ms: 786` | `ttft_sum_ms` + `ttft_count` |
| 缓存命中率 | `cache_rate: 0.35` | `cache_read_tokens` + 三项 token |

`ttft_sum_ms` = 区间内所有**有 TTFT 记录**的请求的首字延迟毫秒数之和；`ttft_count` = 这些请求的条数（非流式或未记录 TTFT 的请求不计入两者）。
便利字段（`availability` / `avg_ttft_ms`）可以同时返回，我方仅用于展示校验；**计算一律以原始值为准**。

## 7. 数据一致性约束

### 7.1 自洽性与容差

以下等式我方会在落库前校验，超出容差记录警告（不阻断落库）：

| 等式 | 容差 |
|---|---|
| `cost_cny ≈ usage_usd × cost_ratio`（`cost_mode="ratio"`） | 相对误差 0.5% |
| `cost_cny ≈ usage_usd × cost_discount × 汇率`（`cost_mode="discount"`） | 相对误差 0.5% |
| `Σ models[].usage_usd ≈ suppliers[].usage_usd` | 相对误差 0.5% |
| 接口 B 按天求和 ≈ 接口 A 整段 | 相对误差 0.5% |
| `availability ≈ request_count / (request_count + error_count)` | 绝对误差 0.001 |

### 7.2 数据完整性与最终一致

`data_complete_before`（Unix 秒）表示：**该时刻之前的数据已最终结算，不会再变动。**

- 我方只会把 `end_timestamp <= data_complete_before` 的部分当作**最终快照**长期保存；
- 之后的部分标记为「未结算」，下次同步时会重新拉取覆盖；
- 若贵方数据是实时的、不存在延迟结算，请返回 `data_complete_before = end_timestamp`（或直接省略，我方按实时处理）；
- 若贵方存在 T+1 对账，请返回昨日结束时刻，避免我方把未结算数据当成最终值。

### 7.3 退款、预扣与异步任务

若贵方支持异步任务（视频生成等）的预扣—结算—退款流程：

- `usage_usd` / `cost_cny` **必须是净额**：预扣 $100 → 全额退款，该区间净额为 `0`；预扣 $100 → 结算补扣 $20，净额 `120`；预扣 $100 → 结算退回 $30，净额 `70`。
- 退款归属到**退款发生的时刻**所在区间，而不是原始请求时刻（否则历史区间的数据会在结算后被追溯改写，我方快照将永远无法达成最终一致）。
- `request_count` 只在**发起**时计 1 次，退款/结算不重复计数。

### 7.4 幂等性

同一组查询参数在 `data_complete_before` 之后重复调用，**必须返回相同结果**。我方的重试机制依赖这一点。

## 8. 错误处理

| HTTP | 场景 | 响应体 | 我方行为 |
|---|---|---|---|
| `200` | 成功 | `{"success": true, ...}` | 正常落库 |
| `200` | 业务失败（如「该聚合渠道未启用成本统计」） | `{"success": false, "message": "..."}` | 不重试，把 message 展示给管理员 |
| `400` | 参数非法 / 区间超出上限 | `{"success": false, "message": "查询区间不得超过 90 天"}` | 不重试，按 message 提示或自动分段 |
| `401` | 令牌无效或过期 | `{"success": false, "message": "..."}` | 不重试，渠道标红提示重配令牌 |
| `403` | 令牌无成本查询权限 | 同上 | 不重试 |
| `429` | 触发限流 | 建议带 `Retry-After` 响应头（秒） | 按 `Retry-After` 退避，最多 3 次 |
| `5xx` | 服务端异常 | `{"success": false, "message": "..."}` | 指数退避重试最多 3 次 |

**`message` 请写给人看**——它会原样出现在我方管理员的界面上。`"error"`、`"failed"`、堆栈片段都是无效信息。

## 10. 常见口径错误（请逐条自查）

以下是我方在自己系统中**真实出现过并已修复**的缺陷，同类实现极易复现：

### 10.1 缓存命中率分母用了总 tokens

```
❌ cache_rate = cache_read / (prompt + completion + cache_read + cache_creation)
✅ cache_rate = cache_read / (prompt + cache_read + cache_creation)
```
输出 tokens 永远不可能命中缓存，计入分母会系统性压低命中率。

### 10.2 缓存创建 tokens 翻倍

```
❌ cache_creation = cache_creation_tokens + cache_creation_tokens_5m + cache_creation_tokens_1h
✅ cache_creation = cache_creation_tokens          // 本身即总量，5m/1h 是它的拆分项
```

### 10.3 `prompt_tokens` 含缓存却当成不含

混合 Claude（互斥）与 OpenAI（含缓存）两种上游时，若不做归一化直接相加：
- 总 tokens 会重复计算 OpenAI 侧的缓存读取；
- 缓存命中率分母偏大或偏小，甚至出现 >100%。

见 §6.2。

### 10.4 时间区间闭合导致重复计数

按天连续拉取 `[D, D+1]` 闭区间时，每个边界秒被计两次。必须左闭右开。

### 10.5 比率字段被二次平均

返回 `availability: 0.99` 而不给分子分母，导致下游汇总时对不同规模的行做算术平均，得出与事实相反的结论。见 §6.7。

### 10.6 异步任务预扣与结算重复计数

预扣一条、结算一条、退款一条——若三条都按正数累加，消耗会虚高。必须按净额。见 §7.3。
